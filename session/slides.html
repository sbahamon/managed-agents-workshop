Say (0:45–2:30)

  • You've all written the Messages API tool loop: you keep the history, you run the tools, and if your process dies the conversation goes with it. Ask the room: where does tool execution run in your last project, and who owns that box?
  • Same model, same tools vocabulary. The difference is who operates each layer.
  • The Agent SDK is Claude Code's agent as a library — "in a process you operate," per the docs. Great harness, but you host it.
  • Managed Agents: "Have Anthropic host the agent, configured through the Claude API." The right-hand column is what you no longer run.

Likely question

  • "Isn't this just Claude Code in a container?" — Similar harness ideas, but the unit is an API resource: versioned agents, an event log you can replay, environments you configure by API, sessions that live without your process.
  • "What about the code execution tool?" — It runs code server-side, but in a container with no internet access and fixed libraries. Fine for analysis; not for "install this vendor package and see what it does."
Be fair to all three

When each one wins

Messages API · still wins

You want the wheel

  • Single calls: classify, extract
  • Your own loop, your control flow
  • Zero Data Retention eligible
Agent SDK · still wins

Your box, your rules

  • Trusted code on runners you have (CI)
  • Works on local files and tools
  • Data stays in your environment
Managed Agents · now wins

You'd rather not host it

  • Long-running: outlives the caller
  • Untrusted code, throwaway sandbox
  • Many users, one versioned definition

Say (2:30–3:45)

  • Not a "use Managed Agents for everything" pitch. Most API calls should stay Messages API calls.
  • Agent SDK still wins when the box is already yours and trusted — e.g. code review on your own repo in CI.
  • Managed Agents wins when you'd otherwise build a container fleet, a job queue, and a state store just to run the agent.
  • Managed Agents is not currently ZDR- or HIPAA BAA-eligible (overview page) — it is stateful by design.

Likely question

  • "Can I migrate between them?" — Yes; there's a migration guide from the Agent SDK. The concepts map; who hosts changes.
Four concepts · one metaphor

Think of a restaurant kitchen

Say (3:45–5:00)

  • Agent = the recipe card: model, system prompt, tools. Created once, referenced by ID, versioned.
  • Environment = how the kitchen is set up: pre-installed packages, which doors are open (networking).
  • Session = cooking one order at its own station — a fresh container per session. Unlike a kitchen, the station is kept for you: idle sessions are checkpointed (files, installed packages), and sandbox state lasts 30 days from creation. Activity doesn't extend it.
  • Events = the call-outs: each step of cooking that order, called out as it happens. "Chopping," "sautéing" (tool use, status), "need a call from the front" (a custom tool, which comes back to you), "order up." You call in too: the order (user.message) and "stop!" (user.interrupt). The steps aren't written on the recipe; the cook picks each one as it goes.

Likely question

  • "Is the environment the container?" — No: it's the template. Each session gets its own container built from it.
One turn · click to step through it

Who does what, and when

Say (5:00–8:30) · 4 clicks

  • Click 1 · you send. Open the stream before you send: a stream only delivers events after it opens. Three lanes: your process, the session (Claude running the loop on Anthropic's side), and the session's sandbox.
  • Click 2 · the sandbox. The built-in toolset (bash, file ops, search) runs in the session's container. You never write a tool executor for those. Untrusted code runs here, not on your laptop.
  • Click 3 · your process. A custom tool is a schema on the agent; execution is yours. Note who asks: the session sends agent.custom_tool_use. The sandbox never calls you. Then the session goes idle with requires_action and lists the event ids it's blocked on. It isn't done; it's waiting on you. In the lab, your first run stalls right here, on purpose.
  • Click 4 · you answer. Send user.custom_tool_result with custom_tool_use_id = that event's id; the session resumes and ends with end_turn. Rule: idle ≠ done.
  • Rule of thumb: needs a disposable box → sandbox. Needs your systems or secrets → custom tool. In the lab UI every tool card is labelled sandbox · bash or local · record_verdict: this slide, live.
  • Two things a kitchen can't do: you can shout "stop" mid-dish (user.interrupt, then a new user.message), and every call-out is written down for good. Events persist server-side, so you can reconnect and replay the whole history. That's the lab's second "work it out."

Likely question

  • "Do I have to wait for the idle event before answering?" — No. You can answer as soon as agent.custom_tool_use arrives; the idle event still comes and you can ignore it.
  • "Why not give the sandbox my DB credentials?" — Then untrusted vendor code in that sandbox can read them too. Keep secrets on your side of the line (or use vaults for MCP credentials).
  • "Does an idle session cost money?" — Session runtime ($0.08/session-hour) is billed only while status is running.
Configuration as a resource

The agent is a versioned API resource

Say (8:30–9:45)

  • With the Messages API or the SDK, "the agent" is a prompt string and a tools list compiled into each app. Here it's a resource with an ID and a version number.
  • Every config change creates a new version. Sessions created with just the agent ID get the latest version at creation time; you can also pin a session to an explicit version for staged rollouts.
  • The ant CLI can apply agent and environment definitions from files, so the definition can live in git and go through code review. (We use the Python SDK in the lab; this is the framing, not the lab task.)

Likely question

  • "How do I roll back?" — Pin new sessions to the previous version number, or update the agent back to the old config (that creates a new version with the old content).
Where the sandbox lives

Cloud environment vs self-hosted sandbox

Sensitive data? Be precise.
  • Managed Agents is not currently ZDR or HIPAA BAA eligible — it's stateful by design.
  • Self-hosted keeps files, processes and egress on your infra — but tool results still reach Anthropic.

Say (9:45–11:00)

  • Cloud environments are configured by API: packages to pre-install and a network policy. limited means only allowed_hosts, plus package registries / MCP servers if you opt in. Omit networking on create and you get unrestricted.
  • Self-hosted: you run a worker; Claude still runs on Anthropic's side and asks your worker to execute tool calls. Use it when files can't leave your network or tools must reach internal services.
  • Be exact with customers: self-hosted moves execution, not the conversation. Tool inputs and outputs still flow to Anthropic's control plane. Not ZDR/BAA-eligible either way today.
  • Beyond today, if asked: memory stores, outcomes (define_outcome), multiagent, vaults, webhooks, scheduled deployments, budgets. A map, not homework; Outcomes is a natural next step after the lab.

Likely question

  • "So can I use this with PHI?" — Not today (no BAA coverage). Self-hosted reduces what leaves your network but doesn't change eligibility.
