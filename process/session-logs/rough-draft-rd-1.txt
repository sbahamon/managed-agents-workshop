  - The work outlives the caller. Close the tab and the agent keeps going.
  - Many isolated runs come from one definition. Each gets its own sandbox, with
    no containers or queues for you to run.
  - The agent definition is shared, versioned infrastructure. Every app that
    uses it gets the same agent.md and the same ID, and running sessions stay
    pinned.
  - A human decision arrives later. The session waits for approval with no
    process of yours held open.

  The scenario should be chosen so the answer to "why not the SDK?" is built
  into how the task runs. The domain matters much less.

  Improved options

  Each fits in about 50 minutes of lab with turns of 1–3 minutes. All use mock
  data, with no third-party APIs.

  1. Fan-out audit ("one definition, many sandboxes"). Learners write agent.md
     and environment.yaml, then ant apply. A script launches about three
     sessions in parallel, one per input (three small mock services or datasets
     to audit). The UI shows a grid of session lanes running at once. Then they
     edit the config, ant apply again to get version 2, and launch a second
     batch. Version 1 and version 2 lanes sit side by side, and the old ones
     stay pinned.
     - Why not the SDK: you'd be building the container pool, the job queue and
       the state store yourself.
     - Risk: three sessions cost about three times as much, though that's still
       cents.
  2. Night-shift agent ("hand off, walk away, approve later"). The agent does
     some real sandbox work, then reaches a consequential custom tool (deploy,
     send_report) gated by always_ask, and the session waits with
     requires_action. Learners kill their app, reopen it from a different client
     (web UI versus CLI), replay the event log, approve, and watch it resume.
     The permission policy is one line of config, so the infrastructure-as-code
     (IaC) angle stays.
     - Why not the SDK: your process would have to stay alive holding the state.
     - Visual: a timeline of session states.
  3. Agent as a platform service ("platform team / app team"). The agent's
     config lives in a git folder as a team-owned resource. Two consumers, a

     pins version 1 and the other follows latest.

     - Weakness: it's the least visual and the most abstract.
  4. Recommended: a combination of 1 and 2. The spine is version 1 fan-out. Then
     the "figure it out" step: change the config so the consequential tool
     needs approval, which gives version 2. Then close the laptop, come back,
     and approve. The stretch goal is Outcomes or a budget.

  The domain can sit inside any of these. Examples are auditing three mock
  microservices' configs, data-quality checks on three dropped CSVs, or reusing
  the cwc incident data.

  For it:

    steps, with files coming back.

  Against it, and this side wins:
  - The Agent SDK on a laptop does it fine, and more simply. pip install osmnx,
    run the agent locally, done. The data is public and trusted, the job takes
    about 2 minutes, and a human watches the whole time. There's no isolation
    need, nothing that outlives the caller, and nothing to share or version.
    Picking Managed Agents here is choosing the bigger tool for a small job, and
    a sharp learner would say so.
  - It teaches the wrong instinct. It quietly suggests "Managed Agents = the one
    with a sandbox." The Agent SDK has sandbox-ish built-in tools too. What
    actually sets Managed Agents apart is that you don't operate the runtime.

  The fix is the framing, not the task. A notebook run by one person on public
  data will always look like an Agent SDK job. It flips when the notebook is the
  backend of a product feature serving many end users. Each request becomes a
  session in its own sandbox, created from one agent definition, and the user
  doesn't stay around to watch. With the Agent SDK you would be operating a
  fleet of containers, isolating them from each other, and storing session
  state. With Managed Agents, that's sessions.create.

  So the notebook narrative becomes: "You're adding a feature to your product.
  Here's the backend for it." It creates the agent and environment once, then
  handles two "customer requests" as two sessions, which shows isolation and
  that the definition is reusable. Images come back through the Files API.

⏺ Your instinct is right. I'd tighten two words before they reach a slide,
  because a security-minded SA in the cohort will push back on them.

  1. "Very thorough SBOM tool" → "SBOM plus behavior." A software bill of
  materials (SBOM) is a deterministic list of what's inside a codebase, and
  tools like syft already produce it better than an LLM would. The agent's value
  is judgment about what the code does: running the install and watching it,
  reading the suspicious postinstall script, running the tests, spotting
  obfuscated code. A nice touch: put syft in the environment's packages. Then
  the agent runs the deterministic SBOM tool and investigates on top of it, and
  the environment config does visible work.

  2. "Airtight sandboxing" → "a fresh, isolated box per repo, with egress you 
  control, that you never operate." "Airtight" is a security claim we can't back
  up, and it's the kind of phrase that costs an instructor credibility. What we
  can say is this: each session gets its own container, networking can be
  locked down to limited plus allowed_hosts (our stretch goal), and the box is
  thrown away afterwards.

  The honest Managed Agents vs Agent SDK argument for this tool:

  With the Agent SDK, the agent runs wherever you run it. Its built-in safety is
  permission rules and an optional sandbox around the operating system on your
  host. That's fine for trusted code. For untrusted code at scale, you'd have to
  build:
  - a container image
  - a fresh container or VM per scan
  - an egress policy
  - cleanup
  - a job queue
  - crash recovery
  - a durable store for transcripts

  With Managed Agents, the per-scan sandbox, its network policy, the loop, and
  the durable event log are all sessions.create.

  The point I'd stress most: the session's event log is the audit trail. A
  verdict on a third-party repo is a security decision, and someone will ask
  "why did it say safe?" The answer is every command the agent ran, stored
  server-side and replayable. That's also why "reattach, don't recreate" matters
  in the lab: the evidence survives your app crashing.

  Where the Agent SDK still wins, which belongs in the instructor guide:
  - Scanning your own trusted code in CI, where the runner is already
    disposable.
  - Code that can't leave your network. Managed Agents' answer there is a
    self-hosted sandbox, which ties back to your PII slide.
  - Needs for Zero Data Retention (ZDR) or full control of the runtime.

  Proposed one-line pitch: "An SBOM tells you what's in it. The agent tells you 
  what it does. Managed Agents gives each untrusted repo a fresh, 
  egress-controlled box you never operate, and keeps every command as evidence."

  **Bugs**
  1. **The notebook stream loop hangs on a failed run.** Reference:
  sentry/managed_agents.py:84-108 stops on every non-requires_action stop
  reason. Its docstring says "breaking only on end_turn would hang forever".
  Ours: repo_health.ipynb cell 8 breaks only on `end_turn`. The 50¢ budget makes
  `budget_reached` likely, and `refusal`, `retries_exhausted` and
  `status_terminated` also hang it. Fix: reuse the `turn_over` rule from the
  lab.
  2. **Cleanup runs interrupt and delete with no wait in between.** Reference:
  knowledge-wiki/utilities.py:28-55 notes that the session status lags the
  event, so an archive sent straight after it returns 400. Ours:
  cleanup.py:36-42. The delete fails, and the archive fallback hits the same 400
  while the session is still running. That exception isn't caught, so the
  script dies before the env/file deletes and `state.forget`. The env delete at
  :51 is also unguarded, and upstream cleanup.py:69 says envs can't be deleted
  while sessions reference them. Fix: after the interrupt, poll
  `retrieve().status` until idle or terminated, with a time limit, then delete.
  Wrap every call so failures are logged and the script continues. Also
  interrupt sessions whose status is `rescheduling`, since the SDK literal
  includes it.
  3. **Sessions in `rescheduling` are never found.** Reference:
  reducer.ts:409-411 treats rescheduled as busy. Ours: provided.py:144-147
  `needs_attention` returns False for them, so reattach misses a session that is
  retrying. Fix: count `rescheduling` as needing attention.

  **Robustness**
  4. **Resume can answer a tool call twice.** Reference: reducer.ts:440 skips
  calls already in `answeredCustomTools`. Ours: provided.py:153-160 doesn't drop
  ids that already have a `user.custom_tool_result` in history. If the process
  crashes after answering but before `status_running`, resume sends the result
  again, and a 400 there ends the resume. Fix: drop ids that already have a
  result.
  5. **A dropped stream ends silently.** Ours: solutions/agent.py:67-72 — if the
  stream ends without a terminal event, `_pump` marks the run DONE and the UI
  shows nothing wrong. Fix: if the loop ends without `turn_over`, fall through
  to `resume()`.
  6. **Pagination costs extra requests.** Iterating a page object
  auto-paginates. provided.py:148 uses `limit=1` inside `list()`, which fetches
  every idle event one request at a time. solutions/agent.py:77 walks all
  sessions and runs an events.list for each idle one. Fix: read `.data` from the
  first page only, or take the first item.
  7. **Agent config never updates.** Reference: upstream state.py:88-118
  fingerprints the config and calls update with `version=` when it changes.

  8. **Handles can collide on a shared key.** Reference: upstream state.py:59
